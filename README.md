# Character Segmentation with GNN

フォント輪郭パスから文字区間を識別する、GNNエッジ分類システム。

<img width="1262" height="430" alt="image" src="https://github.com/user-attachments/assets/e0cdbb55-029e-46e0-a5e9-a562adae2b56" />

## 構成

Rust(データ生成・推論)と Python(学習)のハイブリッド構成。

| コンポーネント       | 言語   | 役割                                                                               |
| -------------------- | ------ | ---------------------------------------------------------------------------------- |
| `crates/glyph-core`  | Rust   | パス抽出・弧長リサンプリング・特徴量生成・KD木グラフ構築(学習/推論で共有)          |
| `crates/dataset-gen` | Rust   | 合成データセット生成(rustybuzz + ttf-parser + rayon)→ MessagePack                  |
| `training/glyph_gnn` | Python | PyG データローダー・エッジ特徴量つき GAT・Focal Loss・採点/分析・ONNX エクスポート |
| `crates/glyph-infer` | Rust   | ort による ONNX 推論・閾値判定・Union-Find 連結成分抽出                            |

## データフロー

```text
fonts/*.ttf ──> dataset-gen ──> dataset/*.msgpack ──> train.py ──> best.pt
                                                          │
demo text ──> glyph-core 前処理 ──> ort 推論 <── model.onnx <── export_onnx.py
                                       │
                                閾値判定 + Union-Find ──> 文字グループ
```

## セットアップ

```bash
# Rust 側(ビルドのみ)
cargo build --release

# Python 側 (uv)。Linux/Windows は CUDA 12.6 版 torch を解決
uv sync
```

## 使い方

### 1. データセット生成(フェーズ1)

```bash
cargo run --release -p dataset-gen -- \
    --body-fonts fonts/body --deco-fonts fonts/deco \
    --count 100000 --out dataset/train
```

日本語データセット例（`charsets/` のプリセットを利用）:

```bash
cargo run --release -p dataset-gen -- \
    --body-fonts fonts/ja-train --deco-fonts fonts/ja-train \
    --charset-file charsets/japanese-mixed.txt \
    --count 100000 --out dataset/ja-train
```

- `--charset` … インラインで文字集合を指定（デフォルトは英数字）
- `--charset-file` … UTF-8 テキストファイルから文字集合を読み込み（`#` 行頭コメントと空行は無視。同一文字の重複は出現率を上げる）
- 同梱プリセット: `charsets/ascii.txt`, `hiragana.txt`, `katakana.txt`, `kana.txt`, `japanese-basic.txt`, `japanese-mixed.txt`
- `--text-file` … ランダム文字列の代わりに固定テキストを1行1件で読み、順番に割り当てる
  （評価用。`--min-chars` / `--max-chars` は効かない）

混同パターン評価セットの生成:

```bash
cargo run --release -p dataset-gen -- \
    --body-fonts fonts/ja-train --deco-fonts fonts/ja-train \
    --text-file texts/confusables.txt --count 20000 --out dataset/confusables
```

`texts/confusables.txt` は過分割・過結合が起きるパターンを集めたもの
（`ll` `rI` `rn` / `こ` `た` `二` `一一` など）。各行が同じ回数だけ、
別々のフォントと拡張で描かれるので、パターン別の一致率をそのまま比較できる。

- 本文フォント:装飾フォント = 7:3(`--deco-ratio` で変更可)
- データ拡張: トラッキング、ベースライン上下動、アスペクト比変更、ポイントノイズ

#### レイアウト拡張の分布

| オプション                 | 既定          | 意味                                                 |
| -------------------------- | ------------- | ---------------------------------------------------- |
| `--tracking-min` / `--max` | −0.18 / +0.02 | トラッキングの範囲(em)                               |
| `--tracking-skew`          | 1.0           | 分布の形。1 で一様、大きいほど `--tracking-max` 寄り |
| `--baseline-jitter`        | 0.06          | 1グリフあたりの縦揺れ上限(em)。0 で無効              |
| `--aspect-x-min` / `--max` | 0.8 / 1.25    | 行全体の横倍率(condensed / extended)                 |
| `--point-noise`            | 0.004         | 全アウトライン点に加えるジッタ上限(em)               |

**トラッキングは1サンプルにつき1回**引かれる。行内でピッチが規則的に保たれ、
それがモデルが必要とする手がかりそのものになる。

#### 分布を実際の用途に寄せる実験 — 効果がなかった

「通常の組版、少しロゴより」を対象とするなら、`Uniform(−0.18, +0.02)` は
コーパスの2/3が実際より詰まった状態になり無駄では、という仮説を測った。
中央値 −0.02 em の偏った分布(skew 1.8、上限 +0.04)と、
`--baseline-jitter` 0.06 → 0.02 を試したが、**全帯で悪化した**。

ja-lyric 4,000サンプル / 10エポック、評価は別シードの固定トラッキング帯
(1,500グラフ、jitter 0)、各モデルは自分の最良閾値:

| 帯 (em)             | 一様(既定) | 偏らせた分布 | 偏らせ + jitter 据え置き |
| ------------------- | ---------- | ------------ | ------------------------ |
| +0.06               | 0.9780     | 0.9813       | 0.9807                   |
| +0.02               | **0.9693** | 0.9667       | 0.9653                   |
| −0.02               | **0.9420** | 0.9400       | 0.9367                   |
| −0.05               | **0.9180** | 0.9093       | 0.9047                   |
| −0.10               | **0.8773** | 0.8447       | 0.8487                   |
| −0.10 (jitter 0.06) | **0.8767** | 0.8487       | 0.8473                   |

- **拡張の広さ自体が正則化として効いている。** 本番域に絞ると、その本番域でも精度が落ちる
- 犯人は tracking の偏り。jitter を 0.06 に戻しても回復しないので、
  `--baseline-jitter` は 0.02 でも 0.06 でも**ほぼ中立**だった
- 上限を +0.04 に伸ばす意味もなかった。一様分布は学習範囲外の +0.06 でも 0.978 出る。
  **緩いテキストは元々簡単**
- そのため既定は測定で勝った一様分布に戻してある。フラグは残す

閾値の較正が交絡することに注意。最初に各モデルの学習検証で決めた閾値
(0.70 対 0.60)のまま帯を測ると「偏らせたほうが過分割が少なく過結合が多い」
と見えるが、帯ごとに最良閾値を取り直すと差は消える。
**モデルの性質ではなく較正のずれ**だった。

**帯ごとの評価セット**は上下を同じ値にすれば作れる:

```bash
for t in -0.02 -0.05 -0.10 -0.18; do
  cargo run --release -p dataset-gen -- \
      --body-fonts fonts/ja-train --charset-file charsets/japanese-mixed.txt \
      --tracking-min=$t --tracking-max=$t --baseline-jitter 0 \
      --count 5000 --out dataset/band$t
done
```

単一の平均値だと、失敗が極端な帯に集中しているのか全帯に散っているのかが
区別できない。前者なら広い裾は本番域に何のコストも払っていないことになる。

#### グラフ構築

- `--knn` / `--radius` / `--contour-bridge` / `--spacing` でグラフ構築パラメータを調整
- **推論時は学習時と同じ** `--knn` / `--radius` / `--contour-bridge` を指定すること
  (`glyph-infer` と `dataset-gen` の既定は knn=8, radius=0.25, contour-bridge=0.35)
- 既存の `dataset/ja-train` や `model.onnx` は `contour_bridge=0` で生成されている。
  ブリッジエッジを有効にするにはデータセットの再生成と再学習が必要

### 2. 学習(フェーズ2)

```bash
uv run python -m glyph_gnn.train --data dataset/train --out training/checkpoints/run --epochs 30
```

- 検証分割はデフォルトでフォント単位のホールドアウト(未学習フォント汎化を測定)
- 損失は**点エッジと輪郭ペアの2段構え**(後述)
- **ベストチェックポイントは完全グルーピング一致率で選択**(後述)
- 学習成果物は `training/checkpoints/<run>/` 配下にまとめる(ディレクトリごと gitignore)
- 起動時にデータセット統計・モデル規模・ハイパーパラメータのサマリを表示し、
  シャード読み込み / エポック / バッチ / 検証の進捗バーを出す
  (パイプ出力時は自動で無効。`--no-progress` で明示的に抑止)
- エポックごとに loss・学習率・経過時間・スループット・GPU ピークメモリ・検証指標を 1 行で出力

#### 損失(何を最適化しているか)

モデルは点エッジごとにロジットを出すが、推論はそれを直接使わない。
輪郭ペアごとに max で潰してから閾値判定する。点エッジだけで学習すると2つ穴がある:

- **規模** — エッジの 75〜79% は同一輪郭内で常に陽性。`same_contour` 特徴量で
  当たるので、損失を占有するだけで何も教えていない
- **プーリング** — 1ペアあたり英数字の中央値で24本。max は残り23本を無視する。
  1本が閾値を超えれば2文字が融合するのに、点エッジ損失から見れば「24本中1本の
  間違い」でしかない。しかも Union-Find で被害が連鎖する

そこで両方のレベルで損失を取る:

```text
loss = (1 - w) * focal(点エッジ)  +  w * focal(輪郭ペアに畳んだロジット)
                  ↑ 同一輪郭内は --intra-edge-weight 倍
```

| オプション            | 既定 | 意味                                            |
| --------------------- | ---- | ----------------------------------------------- |
| `--pair-loss-weight`  | 0.5  | ペア項の比率 `w`。0 で従来の点エッジのみ        |
| `--pair-focal-alpha`  | 0.5  | ペア項の陽性クラス重み                          |
| `--focal-alpha`       | 0.25 | 点エッジ項の陽性クラス重み                      |
| `--intra-edge-weight` | 0.05 | 同一輪郭内エッジの重み。0 で損失から完全除外    |
| `--pair-temperature`  | 1.0  | プーリング温度。0 に近づけると推論の max に一致 |

- 陽性率はレベルによって全然違う(点エッジ 86〜96%、輪郭ペアは日本語56%・英数字20%)
  ので、`alpha` も別々に持たせている。実際の値は `glyph_gnn.analyze` で確認すること
- `--intra-edge-weight` を 0.05 にすると、同一輪郭内エッジの寄与は点エッジ損失の
  79% → 約16% に落ちる。0 にしないのは、その出力を `glyph-infer eval` の
  精度表示と GUI のエッジ重ね描きが使っているから
- プーリングは `logsumexp` ではなく softmax 重み付き平均。`logsumexp` は max を
  `T * log(n)` だけ過大評価し、`n` が 6〜590 と振れるのでペアごとにバイアスが変わる

ja 6,000 サンプル(検証 1,200)での実測、2シード:

| `--pair-loss-weight` | 完全グルーピング一致率 | ペア F1 | 過分割 | 過結合 |
| -------------------- | ---------------------- | ------- | ------ | ------ |
| 0.0(従来)            | 0.7067 / 0.6517        | 0.9602  | 0.0311 | 0.0486 |
| 0.5                  | **0.7692 / 0.7300**    | 0.9755  | 0.0212 | 0.0407 |

過分割と過結合が**両方**下がっている(トレードオフではない)。
スループットへの影響は 219 → 217 graphs/s で 1% 未満。

#### 検証指標(何を測っているか)

損失は点エッジ単位で計算するが、**採点は出荷される判断単位＝輪郭グループで行う**。
この2つは大きく違う:

- エッジの 75〜79% は同一輪郭内で、ラベルは例外なく陽性。しかも `same_contour` は
  入力特徴量なので、この分は自動的に当たる
- 独立した判断である輪郭ペアは全エッジの **0.4〜0.6%** しかない
- 推論は輪郭ペアごとに確率を max で潰すので、偽陽性が増幅される。英数字の中央値は
  1ペアあたり24本なので、点エッジ単位の偽陽性率 1% はペア単位で
  `1 - 0.99^24 = 21%` になる

そのため検証では以下を出す:

| 指標      | 意味                                                        |
| --------- | ----------------------------------------------------------- |
| `pair F1` | 輪郭ペア単位の F1                                           |
| `group`   | 1グラフの分割が完全一致した割合(`@0.70` は最良閾値)         |
| `split`   | 1文字の輪郭が複数グループに割れた割合(「こ」「た」の過分割) |
| `merge`   | 1グループに複数文字が混ざった割合(「ll」「rI」の過結合)     |

`split` と `merge` は同じ閾値の裏表なので、必ず分けて見ること。
毎エポック閾値スイープ(既定 0.30〜0.90 の10点、`--thresholds` で変更可)を回し、
最良閾値での一致率で `best.pt` を選ぶ。追加の順伝播は発生しない。

#### フルコーパスでの実測

`charsets/japanese-lyric.txt`(異体字 3,417)、`fonts/ja-train` 92フォント、
30エポック / 6h 18m (RTX 3060、12.6分/エポック):

```text
best grouping accuracy = 0.9789 @ epoch 29

  thr   pair P   pair R  pair F1  group acc    split    merge
 0.30   0.9992   0.9995   0.9994     0.9756   0.0015   0.0055
 0.50   0.9994   0.9992   0.9993     0.9787   0.0022   0.0036  <- best
 0.70   0.9996   0.9988   0.9992     0.9755   0.0032   0.0027
 0.90   0.9997   0.9977   0.9987     0.9592   0.0063   0.0018
```

1行あたり輪郭 37・輪郭ペア 135 の判断を**すべて当てて初めて1カウント**の指標で
97.9%。文字単位では過分割 0.22% / 過結合 0.36%。

**スイープが平らになったことが最大の変化。** 0.30〜0.75 の全域で 0.974 以上あり、
閾値がほとんど効かない。以前は max プーリングの偽陽性増幅を抑えるため 0.7 まで
上げる必要があり、しかも上げると「こ」の上下の画が落ちるという板挟みだった。
ペア損失で「1本だけ暴走する点エッジ」に直接ペナルティがかかった結果がここに出ている。

- 最良閾値は **0.50**。古い 0.7 という値はもう当てにならない
- ここまでの Tier ごとの寄与は 6,000 サンプルでの A/B で測ったもので、
  **フルコーパスでの Tier 別の寄与は未測定**。この 0.9789 には
  データ規模の効果も含まれる。切り分けたければ
  `--pair-loss-weight 0 --no-contour-layers --no-contour-relations
  --no-global-context` でフルを回して比べること(さらに6時間)

#### GPU メモリ

グリフグラフのエッジ数は 1k〜24k と幅が大きく、GAT の中間テンソルは
すべて `[エッジ数, hidden]` 形状なのでピークメモリはグラフ数ではなく
エッジ数に比例する。そのためバッチはエッジ数の予算で構成する。

- `--max-edges-per-batch`(デフォルト 200,000)… 1 バッチのエッジ数上限。
  実測でエッジあたり約 12 KiB(hidden 128 / layers 4)なので、200,000 で
  ピーク約 2.3 GiB。CUDA out of memory が出たらこの値を下げる
- `--batch-size`(デフォルト 64)… 1 バッチのグラフ数上限として併用
- それでも OOM したバッチはスキップして学習を継続し、エポック末に件数を報告

#### ホスト RAM とパック済みストア

`--data` に `.msgpack` シャードのディレクトリを渡すと全件を RAM に展開する。
シャードは float を MessagePack の配列要素として持つため、デコードは
1 シャード約 8 秒かかり、いったん Python のリストとして実体化される。
22 GiB のコーパスはテンソルで約 27.5 GiB になり、展開中の一時領域も加わるので
32 GiB マシンでは載らない。

`glyph_gnn.pack` で一度フラットなバイナリに変換しておくと、
`train.py` が自動的に検出して `np.memmap` 経由で読む。

```bash
uv run python -m glyph_gnn.pack --data dataset/ja-train --out dataset/ja-train-packed
uv run python -m glyph_gnn.train --data dataset/ja-train-packed --out training/checkpoints/run
```

- 常駐 RAM はデータセット規模から切り離され、OS のページキャッシュ任せになる
  (足りなければ回収されるだけなので、ディスクが許す限りデータセットを増やせる)
- 起動時のシャード読み込みが消える(全体で 9 分 → 0 秒)
- サンプル単位のランダムアクセスなので、全体シャッフルもエッジ予算バッチも
  RAM 版とまったく同じ挙動になる
- `--num-workers` はパック済みストアでのみ有効(RAM 版はグラフが全ワーカーに
  複製されるため無視される)

保存時に冗長な列を落として ja-train で 20.09 → **12.23 GiB**(40% 減)にする。
すべて可逆で、msgpack 版とビット単位で一致することを検証済み。

| 列                                  | 扱い                                            | 削減      |
| ----------------------------------- | ----------------------------------------------- | --------- |
| `edge_features[2]` (`dist`)         | `dx`, `dy` から f32 の同一演算で復元            | −2.62 GiB |
| `edge_features[3]` (`same_contour`) | 0/1 なのでラベルバイトの bit 1 に格納           | −2.62 GiB |
| `edge_index`                        | ノード数の最大が 3,172 なので u16 で保存        | −2.62 GiB |
| `node_ids`                          | 輪郭ID・文字IDを u16 ペアで**追加**(採点に必須) | +0.18 GiB |
| `contour_features`                  | 輪郭スーパーノードの特徴量を**追加**(8次元 f32) | +0.03 GiB |

サイズはディスク以上に重要で、12.23 GiB なら 32 GiB マシンのページキャッシュに
ストア全体が収まる。HDD 上に置いても、ディスクから読むのは 1 エポック目だけで
以降のランダムアクセスはメモリ速度になる(ランダム読みが 9 MB/s しか出ない
HDD では、これがないと 1 エポック 38 分がディスク待ちになる)。

パッキング時に `dist` の復元誤差の最大値を表示するので、可逆性が壊れれば気づける。
フォーマットを変えたら `FORMAT_VERSION` を上げること。古いストアは
再パックを促すエラーで弾かれる。

> **v2 → v3**: 輪郭ID・文字ID(`node_ids`)を追加した。これがないと輪郭グループでの
> 採点ができない(点エッジの代理指標しか測れない)。
>
> **v3 → v4**: 輪郭スーパーノードの特徴量(`contour_features`)を追加した。
> どちらも**データセットの再生成と再パックが必要**(`GraphSample` に列が増えたため)。

`--warm-cache` を付けるとストアを順次読みしてページキャッシュに載せてから学習に入る。
HDD ではコールドなランダムアクセスが 9 MB/s しか出ないのに対し順次は 86 MiB/s 出るので、
1 エポック目をディスク待ちで潰すより先に一括で読んだほうが圧倒的に速い。

ja-train 全体(69,911 グラフ / 7 億エッジ)の実測。**輪郭スーパーノードとペア損失を
入れる前の記録**なので、ログ項目(`val F1(neg)`)もスループットも現在とは違う。
順次読みでディスク待ちが消えるという結論だけが有効:

```text
warmed 12.23 GiB of page cache in 2m 25s
epoch   1/2 | loss 0.0043 | 6m 50s | 154 graphs/s | peak 2.3GiB | val F1(neg) 0.8984
epoch   2/2 | loss 0.0019 | 7m 01s | 150 graphs/s | peak 2.3GiB | val F1(neg) 0.9183
```

2 エポック目も速度が変わらない = ディスク待ちが発生しておらず GPU 律速。
SSD に置ける場合は `--warm-cache` は不要。

### 3. 評価・分析

```bash
# 混同パターン別の一致率(どのパターンで壊れているかを特定する)
uv run python -m glyph_gnn.eval \
    --checkpoint training/checkpoints/run/best.pt --data dataset/confusables

# データセットの構造プローブ(エッジ構成・受容野・連結性の天井)
uv run python -m glyph_gnn.analyze --data dataset/ja-train --limit 300

# 採点コードの自己検査(出荷版ポストプロセッサとの一致を確認)
uv run python -m glyph_gnn.selftest --data dataset/ja-train
```

`eval` は閾値スイープの表と、テキスト別の一致率を悪い順に出す。
`--text-file` で作った固定テキストのシャードに対して使うと、
「総合94%」が「`ll` を40%誤結合している」まで分解される。

`analyze` は3つの構造的な問いに答える。いずれも学習ログからは見えない:

1. **エッジ構成** — 損失が実際に何に使われているか(自明なエッジの割合)
2. **受容野** — L ホップで em 単位でどこまで情報が届くか。1文字分に満たなければ、
   隣の文字が見えていない＝文字ピッチを判断材料にできない
3. **連結性の天井** — 1文字の輪郭同士がそもそもグラフ上で繋がっているか。
   繋がっていなければ、どんな閾値でもモデルでもグループ化できない

`selftest` は `glyph_gnn.metrics` を既知解(オラクル・全結合・全分割)と、
`glyph-infer` の Union-Find を写した `postprocess.group_characters` の
両方に突き合わせる。採点コードが静かにズレると以降の計測が全部狂うので、
採点まわりを触ったら走らせること。

### 4. ONNX エクスポート

```bash
uv run python -m glyph_gnn.export_onnx --checkpoint training/checkpoints/run/best.pt --out model.onnx
```

動的軸(ノード数・エッジ数・輪郭数)でエクスポートし、onnxruntime と PyTorch の
出力一致を自動検証する。

入力は5本: `node_features`, `edge_index`, `edge_features`, `node_contour_ids`,
`contour_features`。**グラフは1つ前提**(推論は1行ずつ)なので、プーリングは
入力全体をひとまとめに縮約し、バッチベクタの入力は要らない。

> 輪郭層より前に作った `model.onnx` は入力が3本なので使えない。
> 再エクスポートが必要。

### 5. 推論(フェーズ3)

```bash

cargo run --release -p glyph-infer -- --model model.onnx \
    demo --font fonts/body/arial.ttf --text "Overlap" --tracking=-0.12

# 評価: 生成済みシャードで精度・レイテンシ計測(フェーズ4)
cargo run --release -p glyph-infer -- --model model.onnx \
    eval --shard dataset/eval/shard_00000.msgpack
```

- 既定で CUDA Execution Provider を登録(RTX 3060)。`--cpu` で CPU 実行
- `--threshold` でエッジ結合確率の判定閾値を調整。**このモデル用の値は学習ログの
  閾値スイープか `glyph_gnn.eval` で決めること**

    ほぼ差がない(前掲の実測表)。閾値が効かなくなったのはペア損失の効果
  - 0.7 は 12k サンプル学習モデル時代の値。当時は max プーリングの偽陽性増幅を
    抑えるため高めが必須で、上げすぎると「こ」の上下の画が落ちる板挟みだった

## モデルアーキテクチャ

- 初期レイヤー: ノード特徴量(13次元)→ hidden への MLP + LayerNorm
- GAT レイヤー x N: エッジ特徴量(4次元)を考慮した GATv2 スタイルの
  マルチヘッド注意。**ONNX エクスポートを保証するため PyG の conv ではなく
  gather / scatter_add のみで実装**(PyG の scatter カーネルは torch.onnx で
  不安定なため)
- **輪郭スーパーノード層 x N**: 各 GAT レイヤーの後に、点ノードを輪郭単位に
  プールして輪郭同士で attention を回し、点ノードに戻す
- **グローバル readout**: 全ノードの mean と max をグラフ単位で取り、
  MLP を通して分類器に渡す
- エッジ分類器: `[h_src, h_dst, |h_src - h_dst|, edge_attr, global]` → MLP → ロジット

### 受容野をどう広げているか

4層のメッセージパッシングで届く x 方向の距離は **0.43 em(英数字)〜0.50 em(日本語)**。
行幅は 3.6〜5.9 em なので、1ノードは行の 8〜12% しか見えていない。1文字分にも
足りないので、あるエッジは隣のグリフを一度も見ないまま判断している。
「ll」が2文字か1つの幅広グリフかを分けるのは文字ピッチだが、それは2〜3文字ぶんの
スケールにしか存在しない。層を積むのは筋が悪く、8層でも 1 em に届かずコストは倍になる。

そこで3つ入れている。ja 6,000 サンプル(検証 1,200)での実測:

| 構成                 | seed 5     | seed 99    |
| -------------------- | ---------- | ---------- |
| どれもなし           | 0.7692     | 0.7300     |
| + グローバル readout | 0.7875     | 0.7525     |
| + 輪郭スーパーノード | 0.8633     | 0.7725     |
| **+ 輪郭ペアの幾何** | **0.8742** | **0.8233** |

**輪郭スーパーノード**(`--no-contour-layers` で外せる)が本命。1画がまるごと1トークンに
なり、1行はたかだか 10〜18 個なので、**行全体を張る attention が数%のコストで済む**
(18² ペア対 6,000 点エッジ)。点ノードから見ると、同じ行のどの点にもスーパーノード
経由で2ホップで届く = 受容野が構造的に行全体になる。

- attention は隣接リストではなく dense。推論は1行ずつなので、ONNX に落ちるのは
  素の `[C, C]` 積になり、隣接テンソルの入力が要らない。マスクは学習バッチが
  グラフ境界を越えて attend しないためだけに存在する
- スーパーノードは自前の幾何量(重心・bbox・弧長・**符号付き面積**)から始まる。
  符号付き面積の符号は巻き方向で、カウンター('o' の内側や 'あ' の輪)を見分ける
- **グローバル readout** は輪郭層を入れるとほぼ冗長になる
  (seed 5 で 0.8633 対 0.8600、誤差の範囲)。既定では両方 on

**輪郭ペアの幾何**(`--no-contour-relations` で外せる)は、輪郭特徴量から
その場で導出する11次元。bbox の x/y 重なり(em 単位の符号付きなのでギャップも
同じ軸で表せる)・重なり率・**内包の深さ**・弧長比・**巻き方向の一致**。

- 保存はしない。エッジ列として持つと ja-train の 7 億エッジで **+13 GiB** になる
  (`dist` 1本で 2.62 GiB)。しかも全部、既にメモリにある輪郭2行の関数
- 点レベルの特徴量では表現できない区別を運ぶ。「ll」の2本のステムは
  **x が重ならずギャップは em の何分の一**。「二」の2画は **x が完全に重なって
  y に積まれている**。カウンターは**巻きが逆で、相手の bbox の内側に収まる**
- 輪郭 attention では**ヘッドごとのバイアス**として入る。「重なっているか」は
  ペアの性質で、attention スコアが指すのはまさにペアだから
- パラメータ増は +1,600。スループットは 1 エポック単位で **約10%** 落ちる
  (hidden 128 / layers 4 で 91 → 82 graphs/s)。関係量の計算自体は
  1 ステップ 359ms 中 12.7ms だが、要素演算が30個ほど並ぶので
  エポック全体ではそれより効く

段階ごとの内訳(seed 5、検証 1,200):

|              | 閾値 | 一致率     | ペア F1 | 過分割     | 過結合     |
| ------------ | ---- | ---------- | ------- | ---------- | ---------- |
| readout のみ | 0.75 | 0.7875     | 0.9758  | 0.0222     | 0.0341     |
| + 輪郭層     | 0.65 | 0.8633     | 0.9895  | **0.0123** | 0.0237     |
| + ペア幾何   | 0.65 | **0.8742** | 0.9915  | 0.0128     | **0.0192** |

ペア幾何の効きは過結合側に偏る(0.0237 → 0.0192、相対 -19%)。狙いどおり、
横並びのステムを分けるほうに効く。

- `batch=None` のときは全ノードをプールする。**ONNX が辿るのはこの経路だけ**
  (推論は1行ずつなので)。おかげでエクスポートの入力は3本のままで、Rust 側の
  変更は不要。学習経路との一致は `glyph_gnn.selftest` が検査する
- x のフーリエ符号化(sin/cos、波長 0.5/1/2 em と 1/2/4 em の両方)も試したが、
  **どちらも悪化した**(0.7875 → 0.7500 / 0.7583、2シードで再現)。
  サンプル点の間隔が 0.05 em なので、長いほうの波長でも符号化が速く回りすぎ、
  全アテンション層に入る encoder にとってはノイズになる。不採用

### グラフ表現

- ノード = 輪郭を弧長等間隔でリサンプリングした点
  (座標・接線・重心オフセット・輪郭重心・バウンディングボックス・弧長・輪郭位相)
- エッジ = KD木による半径つき kNN(既定: k=8, r=0.25em) + 輪郭ペアのブリッジエッジ
  (各輪郭の最近接点を `contour_bridge` 以内で接続。kNN 上限で同一文字の遠い
  ストロークが繋がらない問題を解消)、無向(双方向格納)
- 輪郭スーパーノード = 輪郭ごとに1行(8次元: 重心・bbox 幅高・bbox 左下・弧長・
  符号付き面積)。エッジリストは持たない(同一グラフ内は全結合とみなす)
- 輪郭ペアの幾何(11次元)は保存せず、上の8次元からモデル内で導出する
- ラベル = 両端ノードが同一文字(シェーピングクラスタ)に属するか
- 輪郭ID・文字IDもノードごとに持つ(採点とグルーピングに必須)

## 日本語対応

パイプライン(rustybuzz シェーピング → 輪郭抽出 → グラフ化)は文字体系に
依存しないため、**学習データに日本語を含めることで対応する**。

- `dataset-gen --charset-file`（または `--charset`）にかな・漢字を指定し、日本語フォントのプールを
  `--body-fonts` に渡す(`.ttc` コレクションはフェイス0で読み込み対応済み)
- 漢字は1文字が多数の輪郭(ストローク)で構成されるためグラフが大きく、
  英数字より推論コストが高い(実測 約6ms/件 @ RTX 3060)
- 完全グルーピングの難度も高い: 1文字内の全ストロークを結合できて初めて
  正解となるため、境界 F1 の要求水準が英数字より厳しい
- 英数字+日本語の混合データセットで学習しても英数字側の精度は劣化しない
  (実測ではむしろ向上)

## リスク対応(計画書より)

- **特徴次元の可変化**: `NODE_DIM` / `EDGE_DIM` は `glyph-core` の定数と
  モデルの `--hidden` 等ハイパーパラメータで一元管理。チェックポイントに
  hparams を保存し、エクスポート時に自動復元
- **推論前処理のボトルネック**: 前処理は現状 1〜2ms(10文字・CPU)。
  ボトルネック化した場合は KD木を均一グリッド(空間ハッシュ)に置換可能な
  よう `graph.rs` の近傍探索を分離済み
